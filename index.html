How I work

Most of these were built in long autonomous runs. That only works with real discipline around it.

Brief first

Lock the goal before writing code

Every substantial build starts with a written brief naming the goal, the non-goals, and the done-bar. It exists because the expensive failure isn't bad code — it's spending hours perfectly executing the wrong objective.

Blind critics

Grade it against a bar set in advance

Finished work goes to independent critics who haven't seen the brief, scored against a number chosen before the build started. The Red Archive went through seven rounds.

Honour the gate

Don't ship the ones that miss

PANE — a webcam face-tracking illusion that turns a monitor into a window — scored 7.53 against a 9.0 gate. It works, and it stayed unshipped. A bar you move isn't a bar.

Real clicks

Test what the user actually sees

Verification happens through real input on a visible page, never synthetic events in a hidden tab. A dispatched event once "passed" a test on a page covered by an invisible overlay.

About

I'm a high-school student who builds constantly — sixty-five projects across interactive websites, games, AI tooling and trading systems. I play viola, which is why a suspicious number of these end up being about music.

What I care about is the gap between "it works on my machine" and "a stranger can use it." Most of my projects are visual-first: I'd rather a thing communicate through motion and atmosphere than through a wall of on-screen text.

I write in TypeScript, Python and GDScript, and I'm most comfortable in the messy middle — WebGL, canvas rendering, procedural generation, local model serving, and the pipelines that hold them together.
